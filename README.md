# Super Line Adventure

An original 2D side-scrolling platformer built with TypeScript and
Babylon.js v7. 4 hand-authored worlds, 32 individually designed campaign
levels, a procedural Endless Mode, and a fully procedural (zero external
audio files) sound engine. Ships as a web build and as an Android app
(a thin WebView wrapper around the same web build).

## Project structure

```
web/                    the actual game — TypeScript + Babylon.js, built with Vite
  index.html             real entry point (loaded by Vite directly)
  src/
    main.ts              boots the game
    game/GameManager.ts   top-level game state machine
    player/               hero controller, physics, animation states
    enemies/               enemy AI (8 archetypes; some double as bosses)
    levels/
      map1/ .. map4/       hand-authored level data, 8 levels per world
      LevelData.ts          aggregates all 32 levels into ALL_LEVELS
      LevelManager.ts        loads/renders/updates the active level
    endless/               procedural Endless Mode generator
    ui/UIManager.ts         wires index.html's DOM ids to game state
    audio/                 procedural Web Audio synth engine
    storage/SaveManager.ts  localStorage-backed save/settings
    styles/                 hand-written CSS (no framework)

app/                    Android wrapper (Kotlin + Jetpack Compose).
                        MainActivity hosts a WebView pointed at
                        file:///android_asset/game/index.html, plus a
                        native AdMob banner and a JS bridge for
                        interstitial/rewarded ads (see Ads below).
  src/main/java/com/example/ads/AdManager.kt   Google Mobile Ads wrapper
```

## Running the web build

```
cd web
npm install
npm run dev      # local dev server (Vite)
npm run build    # production build -> web/dist/
```

## Building the Android app

The Android app doesn't build the web game itself — it just serves a
pre-built copy from its assets. Before opening the project in Android
Studio, generate a fresh web build and copy it in:

```
cd web
npm install
npm run build
cp -r dist/* ../app/src/main/assets/game/
```

Then open the repository root in Android Studio and run the `app`
module normally. `app/src/main/assets/game/` intentionally ships empty
(see the `BUILD_REQUIRED.txt` placeholder there) rather than with a
stale prebuilt bundle — always regenerate it from current source before
building an APK/AAB, since a mismatched bundle would silently ship an
outdated version of the game.

The Android `applicationId` (`com.aistudio.superline.xkpz` in
`app/build.gradle.kts`) is a placeholder generated by the original
project scaffold — change it before a real Play Store release.

## Ads (AdMob)

The Android app shows three ad formats via Google Mobile Ads:

- **Banner** — persistent, docked at the bottom of the screen. Hidden
  automatically during active gameplay (`UIManager.showScreen` toggles
  it) so it never covers the HUD or touch controls; visible on every
  menu/results screen.
- **Interstitial** — shown automatically on Game Over and on Level
  Complete.
- **Rewarded** — a "Watch Ad: +50 Coins" button on both the Game Over
  and Level Complete screens. Coins are only granted if the ad SDK's own
  reward callback fires (i.e. the player watched to completion), and the
  button disables itself after one claim per screen-visit so it can't be
  farmed by repeat clicks on the same results screen.

**Before a real release, you must replace the test IDs** in two places
with your own from https://apps.admob.com:
- `app/src/main/AndroidManifest.xml` — the `APPLICATION_ID` meta-data
- `app/src/main/java/com/example/ads/AdManager.kt` — the three
  `*_AD_UNIT_ID` constants

Until you do, the app will only ever show Google's official test ads
(clearly labeled "Test Ad" by the SDK) — this is intentional and safe
to ship during development, since using real production ad unit IDs
without going through AdMob's own app-approval flow violates AdMob's
policies anyway.

Ads are the one deliberate exception to this project's "no network
dependency" design — real ads require internet access and Google Play
Services, so `INTERNET`, `ACCESS_NETWORK_STATE`, and the AdMob-required
`AD_ID` permissions were reintroduced specifically for this feature
(they'd been removed in an earlier cleanup pass when nothing used them).

The web side (`web/src/ads/AdsManager.ts`) talks to the native ad code
through `window.AndroidAds`, which only exists inside the Android
WebView wrapper. Every method no-ops safely in a plain browser (e.g.
`npm run dev`), so the web build stays fully playable without the
Android shell — you just won't see any ads there, by design.

## Notes on scope

- All 32 campaign levels (`web/src/levels/map1` .. `map4`) are
  individually hand-authored — no level is a copy of another with only
  numbers changed.
- Other than the ads system described above, the game has no network
  calls and no server-side dependency; the Android wrapper's dependency
  list reflects that (Compose + WebView + Google Mobile Ads only — no
  Firebase, no Room, no networking/analytics stack).
- `web/src/levels/LevelData.ts` retains one leftover
  `generatePlaceholderLevel` function that is no longer used anywhere
  (superseded by the hand-authored map files) — kept as inert dead code
  for reviewability rather than deleted outright; safe to remove in a
  follow-up pass.
